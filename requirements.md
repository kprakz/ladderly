# Ladderly: Requirements

## 1. Purpose

Many people want to learn a skill but never start because they don't know where to begin. Ladderly turns any skill or topic into a short, structured learning path from zero to competent. It gives clear stages, practice and measurable checkpoints, so the learner always knows the next step.

## 2. Users

| User | Need |
|---|---|
| Learner | Types a skill, gets a clear plan, and tracks progress through it. |
| Visitor (web demo) | Tries the app from a shared link without installing anything or paying. |
| Desktop user | Runs Ladderly as a Windows app, including offline in demo mode. |
| Owner / developer | Runs, deploys and extends the app without exposing their API key or running up costs. |

## 3. Functional requirements

### 3.1 Input

| ID | Requirement |
|---|---|
| FR-1 | The user can enter a skill or topic in one text box (1–120 characters). |
| FR-2 | The user can optionally choose a current level: none, some or intermediate. |
| FR-3 | The user can optionally enter hours per week (whole number, 1–80). |
| FR-4 | The user can optionally choose a goal: hobby, job or exam. |
| FR-5 | The server rejects invalid input with a clear message (HTTP 400). |

### 3.2 Learning path content

| ID | Requirement |
|---|---|
| FR-6 | Each path has a one-line summary of what "competent" means for the skill. |
| FR-7 | Each path has 4–6 ordered stages. |
| FR-8 | Each stage has a title and an estimated duration. |
| FR-9 | Each stage lists 3–6 short concepts to learn. |
| FR-10 | Each stage has 1–2 hands-on practice tasks. |
| FR-11 | Each stage has 2–5 concrete, testable "you're ready to move on when…" checkpoint items. |
| FR-12 | Each stage suggests 2–3 *kinds* of resources (e.g. "the official docs"). No URLs and no invented titles. |
| FR-13 | Each path has a finish line: one final project or test that proves competence. |
| FR-14 | Each path lists exactly 3 common pitfalls. |

### 3.3 Generation

| ID | Requirement |
|---|---|
| FR-15 | With an API key configured and demo mode off, paths are generated by Claude (Anthropic API) on the server. |
| FR-16 | Claude is asked for strict JSON matching the path schema, and every response is validated with zod before it is shown. |
| FR-17 | The response is streamed, and the UI shows progress (stage titles as they arrive) while waiting. |
| FR-18 | Starting a new generation cancels any generation already in progress. |

### 3.4 Display

| ID | Requirement |
|---|---|
| FR-19 | The path is shown as a vertical timeline of stage cards. |
| FR-20 | Every checkpoint item has a checkbox. |
| FR-21 | Each stage shows its own progress (checked / total). A completed stage is visibly marked done. |
| FR-22 | The path shows overall progress as a percentage. |
| FR-23 | The finish line and pitfalls are shown after the timeline. |

### 3.5 Saving and history

| ID | Requirement |
|---|---|
| FR-24 | Generated paths and their checkbox progress are saved automatically on the user's device. |
| FR-25 | A "Your paths" list shows past paths with their date and progress. Selecting one shows it. |
| FR-26 | The user can delete a saved path, after confirming. |
| FR-27 | Saved data that no longer matches the expected format is ignored instead of crashing the app. |

### 3.6 Errors

| ID | Requirement |
|---|---|
| FR-28 | API failures (bad key, rate limit, connection, server error), refusals, cut-off responses and invalid JSON each show a clear, user-friendly message. |
| FR-29 | Every error message has a Retry button that re-sends the same request. |

### 3.7 Appearance

| ID | Requirement |
|---|---|
| FR-30 | Clean, minimal design that works on phone, tablet and desktop widths. |
| FR-31 | Light and dark mode. It follows the system setting by default, with a toggle that is remembered. |

### 3.8 Demo mode

| ID | Requirement |
|---|---|
| FR-32 | Demo mode serves built-in sample paths and never calls the paid API. |
| FR-33 | Demo mode is on when `DEMO_MODE=true`, and **always** on when no API key is set. |
| FR-34 | Hand-written samples exist for guitar, public speaking and python (keyword match, case-insensitive). Other topics get a generic template naming the topic. |
| FR-35 | Demo responses stream like real ones, so the loading preview behaves the same. |
| FR-36 | A banner tells users when demo mode is on and which topics have full samples. |

### 3.9 Desktop app (Windows)

| ID | Requirement |
|---|---|
| FR-37 | Ladderly installs on Windows as a normal app, with an installer, Start menu and desktop shortcuts, and an uninstaller. |
| FR-38 | The desktop app works without internet in demo mode. |
| FR-39 | The user can add an API key through a settings file, opened from the app menu (File → Open Settings File). A restart applies it. |
| FR-40 | Links to other websites open in the user's default browser, not inside the app. |
| FR-41 | Only one copy of the app runs at a time. Launching it again focuses the open window. |
| FR-42 | Saved paths persist between app launches. |
| FR-43 | If the app cannot start, it shows an error dialog instead of failing silently. |

### 3.10 Web deployment

| ID | Requirement |
|---|---|
| FR-44 | The same code deploys to Vercel as a public website in demo mode, with no configuration. |

## 4. Non-functional requirements

| ID | Category | Requirement |
|---|---|---|
| NFR-1 | Security | The Anthropic API key is only ever read on the server. It is never sent to the browser or the desktop window, never committed to git, and never bundled into the installer. |
| NFR-2 | Security | The desktop window runs with context isolation and sandboxing, and without Node.js access. The local server listens on 127.0.0.1 only. |
| NFR-3 | Cost | A deployment without an API key can never make paid API calls (see FR-33). |
| NFR-4 | Performance | The first visible progress appears within about 1 second in demo mode. Real generation streams progress instead of blocking. |
| NFR-5 | Accessibility | Form fields have labels, progress bars have ARIA values, errors are announced as alerts, and all controls are keyboard-usable. |
| NFR-6 | Reliability | Invalid or truncated model output never reaches the UI unvalidated (see FR-16). |
| NFR-7 | Maintainability | Every function has a short description of what it does, its inputs and its output, with data types. The code is split into small modules with one job each (see `design.md`). |
| NFR-8 | Compatibility | Web: current Chrome, Edge, Firefox and Safari. Desktop: Windows 10/11, 64-bit. Development: Node.js 20.9+. |

## 5. Constraints and assumptions

- Stack: Next.js (App Router), TypeScript, Tailwind CSS, zod, the Anthropic TypeScript SDK and Electron.
- Model: `claude-opus-5`, with server-side refusal fallbacks enabled.
- Progress is stored per device (browser localStorage). There are no user accounts and no sync between devices.
- The desktop installer is not code-signed, so Windows SmartScreen may show a warning on first run.

## 6. Out of scope

- User accounts, cloud sync and sharing paths with others
- Editing generated paths
- Links to specific external resources
- macOS, Linux and mobile app-store builds
- Automatic updates for the desktop app

## 7. Acceptance checks

| Check | Covers |
|---|---|
| `npx tsc --noEmit` and `npm run lint` pass | NFR-7 |
| `npm run build` succeeds with no key, and the site shows the demo banner | FR-33, FR-36, FR-44 |
| Requests for guitar, public speaking, python and an unknown topic each stream `delta` events and end with a valid `done` event | FR-32 to FR-35 |
| An empty topic returns HTTP 400 | FR-5 |
| Ticking checkboxes updates the stage and overall progress, and survives a reload | FR-20 to FR-24 |
| `npm run desktop:build` produces `dist/Ladderly Setup <version>.exe`, and the installed app opens and generates a demo path offline | FR-37, FR-38 |
| The packaged app contains no `.env` files | NFR-1 |
